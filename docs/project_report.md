## 1. Why this project was chosen

### 1.1 The starting point: the role

The Data Analyst advert describes a job that is mostly **not** chart-making. Its duties are:

| Duty from the advert |
| --- |
| Collect, collate, clean, validate and analyse data |
| Maintain regional datasets |
| Reconcile datasets; identify anomalies, inconsistencies, duplicate records |
| Analyse trends |
| Prepare reports, dashboards and visualisations |
| Work with SQL, Python and Excel |
| Produce evidence to support decision-making |
| Handle data confidentiality |

The advert is effectively a specification for a portfolio project. The goal therefore was not
"build something impressive with data" but **build the exact workflow the advert describes, on
subject matter close to theirs, and leave evidence at every step.**

### 1.2 Why this project and not a generic dashboard

A generic sales dashboard demonstrates visualisation only. This project was chosen because it
forces **every** listed duty into one small pipeline:

| Advert duty | Where it lives in this project |
| --- | --- |
| Collect / clean / validate | `src/generate_data.py` → `src/data_cleaning.py` |
| Maintain datasets | CSV master files + SQLite dimensional schema |
| Reconcile records | claimed distance vs reference distance (17 discrepancies) |
| Find duplicates | 8 duplicates detected and excluded |
| Detect anomalies | 20 km tolerance rule, IQR cost rule, missing/invalid value rules |
| Analyse trends | monthly and weekly cost/volume trend queries and charts |
| Reports and dashboards | Excel dashboard, SQL results file, two written reports |
| SQL | 6-table SQLite database + 9 queries |
| Python | five scripts covering generation, cleaning, loading, analysis, reporting |
| Evidence for decisions | 3 routes flagged **with the rules that flagged them stated** |
| Confidentiality | entirely synthetic data, labelled on the dashboard, README and summary |

Petroleum transport was chosen because it is a **regulated, reconciliation-heavy domain**: every
shipment has a claimed distance, a reference distance, a volume and a cost — which is exactly what
makes reconciliation and anomaly detection meaningful rather than decorative.

### 1.3 Why synthetic data — and why it is labelled

Real regulatory data cannot be used in a portfolio, and inventing numbers while implying they are
real would be both misleading and a confidentiality problem. So:

- Every record is **generated by code** (`src/generate_data.py`, `SEED = 42`).
- The dashboard carries a red italic line: *"SYNTHETIC PORTFOLIO DATASET — fictional petroleum
  product movements. Not an ERB dataset and not a representation of the UPP model."*
- The README repeats the disclaimer in a blockquote.
- No output claims to be an actual tariff, UPP calculation or company performance figure.

The benefit of generating rather than hand-writing the data is **reproducibility**: any reviewer
can run one command and get byte-identical inputs.

### 1.4 Scope discipline

Deliberately excluded: a web application, an API, machine learning, a UPP calculator, a large
dataset and a long report. A small project that is correct, documented and reproducible is far
stronger evidence than a large one that cannot be re-run. The core pipeline takes seconds to run.

## 2. The dataset

### 2.1 What one record represents

One row = **one fictional consignment of petroleum product moved from a depot to a destination**.

| Column | Meaning |
| --- | --- |
| `record_id` | surrogate key, 1–408, unique per physical row |
| `shipment_id` | business key `SHP-0001`…`SHP-0400` (repeats on duplicates, by design) |
| `shipment_date` | 2026-07-01 to 2026-09-30 (one quarter) |
| `company` | one of 6 fictional oil marketing companies |
| `depot` | loading point (Lusaka, Ndola, Kitwe, Kabwe, Livingstone, Kasama) |
| `product` | Petrol, Diesel, Kerosene, Jet A-1 |
| `destination`, `province` | delivery point and Zambian province |
| `volume_litres` | 24,000–40,000 L (road tanker loads) |
| `reference_distance_km` | verified distance from the maintained route table |
| `claimed_distance_km` | distance as claimed by the transporter |
| `transport_cost` | cost in ZMW |

**Scale:** 400 generated records + 8 duplicated rows = **408 rows**, 26 routes, 21 destinations,
9 provinces.

### 2.2 Reference data

Reference distances come from a route table built into the generator (e.g. Lusaka → Kabwe 130 km,
Ndola → Kitwe 65 km, Lusaka → Choma 320 km). Costs are then derived from
`volume × reference distance × route rate (0.0040–0.0050 ZMW/litre-km) ± noise`, so the clean data
has a realistic, tight cost structure that anomalies can be measured against.

### 2.3 Deliberate data-quality defects

Defects are injected on **disjoint** row sets so counts are exact and reproducible:

| Defect | Count | Real-world analogue | How it is detected |
| --- | ---: | --- | --- |
| Distance discrepancy (claimed ≠ reference > 20 km) | 17 | disputed mileage claims | `ABS(claimed − reference) > 20` |
| Missing claimed distance | 11 | incomplete waybill capture | null after numeric coercion |
| High-cost anomaly | 9 | unusually expensive trip | cost/litre-km > Q3 + 3 × IQR |
| Duplicate record | 8 | re-keyed / re-imported transaction | full-row duplicate (excluding surrogate key) |
| Missing company or depot | 6 | unidentified party or origin | blank key field |
| Invalid volume (0, −5000, "N/A") | 4 | keying error | value ≤ 0 or non-numeric |
| Inconsistent product names (`diesel`, `DIESEL`, `" Petrol "`) | 26 cells | uncontrolled free text | standardised on load |
| Thousand-separator text in cost (`"18,500"`) | 3 cells | export formatting artefacts | commas stripped, then coerced |
| Invalid date | 0 | corrupt date field | `to_datetime(errors="coerce")` (rule tested, none found) |

### 2.4 Integrity decisions

- **Surrogate key.** `shipment_id` cannot be a primary key because duplicates share it — exactly
  the situation a real warehouse faces. `record_id` was added as the surrogate; the database and
  the exception register both key on it.
- **Severity model.** `High` = hard validation failure (missing, invalid, or out-of-tolerance
  value). `Medium` = duplicate or statistical flag that needs human judgement. This distinction
  prevents a statistical suspicion being presented as a proven error.
- **Seeded generation.** `numpy.random.default_rng(42)` — every run reproduces the same 408 rows
  and the same 55 issues.

## 3. How it was executed

### 3.1 Pipeline

```text
src/generate_data.py          408 raw records + injected defects
        ↓
src/data_cleaning.py          standardise → coerce → validate → flag → clean set
        ↓                      + data quality report
src/load_database.py          6-table SQLite warehouse (foreign keys enforced)
        ↓
src/run_queries.py            9 analytical queries → results file
        ↓
src/analysis.py               route cost metrics → flagged routes + summary
        ↓
dashboard/build_dashboard.py  Excel dashboard (KPIs, charts, register)
```

Run all of it:

```bash
pip install -r requirements.txt
python src/generate_data.py
python src\data_cleaning.py
python src/load_database.py
python src/run_queries.py
python src/analysis.py
python dashboard/build_dashboard.py
```

### 3.2 Stage 1 — Generation

`src/generate_data.py` draws routes with depot-based weights (Lusaka is busiest), assigns dates
across the quarter, computes cost from the route rate, then injects the defect table above and
appends 8 exact duplicate rows. Output: `data/raw_data.csv`.

### 3.3 Stage 2 — Cleaning and validation

`src/data_cleaning.py` runs the stages below in order, writing a flag for anything that fails:

```text
Read raw → standardise text → reformat numerics → parse dates
    → detect duplicates → validate fields → compute cost threshold
    → flag records → split clean vs exceptions → write report
```

**Rules applied**

| Rule | Threshold | Outcome |
| --- | --- | --- |
| Product/field standardisation | strip + canonical case | 26 product names corrected |
| Numeric reformatting | remove thousands separators | 3 cost values recovered |
| Distance tolerance | > 20 km difference | 17 flagged `High` |
| Volume validity | ≤ 0 or non-numeric | 4 flagged `High` |
| Missing claimed/reference distance | null after coercion | 11 flagged `High` |
| Missing company/depot/destination | blank | 6 flagged `High` |
| High-cost anomaly | cost/litre-km > Q3 + 3 × IQR = **0.00639** | 9 flagged `Medium` |
| Duplicate row | identical across all fields except `record_id` | 8 flagged `Medium` |
| Date validity | unparseable | 0 flagged |

Cost per litre-km is normalised on **reference** distance so that a disputed claim cannot inflate
or deflate the anomaly test.

**Outputs**

| File | Rows | Purpose |
| --- | ---: | --- |
| `data/processed_data.csv` | 408 | full master with `quality_status` (clean/flagged) |
| `data/cleaned_data.csv` | 353 | analysis-ready set |
| `data/issues_flagged.csv` | 55 | exception register with severity and detail |
| `reports/data_quality_report.md` | — | counts, actions taken, thresholds used |

**Detail level:** each exception carries a human-readable reason, e.g.
`claimed 125 km vs reference 40 km (difference 85 km)` or
`0.00782 ZMW per litre-km exceeds threshold of 0.00639`.

### 3.4 Stage 3 — Database

`src/load_database.py` builds `data/warehouse.db` as a small dimensional schema rather than a flat
copy of the CSV, so joins and referential integrity are real:

| Table | Rows | Role |
| --- | ---: | --- |
| `companies` | 7 | dimension (incl. `(not supplied)` for missing values) |
| `depots` | 7 | dimension |
| `destinations` | 21 | dimension with province |
| `routes` | 26 | reference: depot × destination × reference distance |
| `shipments` | 408 | fact, with `quality_status` |
| `shipment_issues` | 55 | exception fact, FK → `shipments.record_id` |

Foreign keys are enforced during load and verified with `PRAGMA foreign_key_check` → **0
violations**. Missing companies/depots map to an explicit `(not supplied)` member instead of
silently dropping rows.

### 3.5 Stage 4 — SQL

Nine queries in `sql/analysis_queries.sql`, executed and captured by `src/run_queries.py` into
`sql/query_results.md`:

| # | Query | Purpose |
| ---: | --- | --- |
| 1 | Headline KPIs | single-row control totals |
| 2 | Volume by product | mix |
| 3 | Volume by province | regional demand |
| 4 | Average cost by destination | cost concentration |
| 5 | Monthly volume and cost trend | trend |
| 6 | Suspicious distance claims | **reconciliation** |
| 7 | Issues by category | **data quality** |
| 8 | Highest cost/litre-km routes | **ranking** |
| 9 | Exceptions by company | **accountability** |

Analytical queries filter `quality_status = 'clean'`; reconciliation and quality queries inspect
the flagged records. Keeping those two populations separate is the core discipline of the project.

### 3.6 Stage 5 — Analysis

`src/analysis.py` answers one question: **which routes require further investigation?**

1. Cost per litre = transport cost ÷ volume.
2. Cost per litre-km = transport cost ÷ (volume × **reference** distance).
3. Roll up per-route across the 353 clean records; compare with the network average of
   **0.004431 ZMW per litre-km**.
4. Flag a route if **either**:
   - route cost/litre-km is **≥ 10%** above the network average (materiality rule), or
   - the route carries **≥ 2** high-cost anomaly records (repeat exceptions, not one-off variance).

Both rules are stated in the output — the conclusion is auditable. Outputs:
`data/route_metrics.csv` (26 routes) and `reports/analytical_summary.md`.

### 3.7 Stage 6 — Dashboard

`dashboard/build_dashboard.py` generates `dashboard/ERB_transport_dashboard.xlsx`:

- **KPI row:** Shipments analysed (353) · Volume moved (11,562,000 L) · Avg transport cost
  (ZMW 39,733) · Data quality issues (55).
- **Five visuals:** volume by product, volume by region, average cost by destination (top 10),
  weekly cost trend, issues by category.
- **Routes flagged** block (3 rows) and the **full 55-row exception register** colour-coded by
  severity.
- Supporting tables live on a `Data` sheet that every chart references — charts are not pasted
  images.
- A method/sources panel records the rules, thresholds and generating script.

`dashboard/powerbi_build_spec.md` is the equivalent build specification for Power BI Desktop:
import steps, relationships (keyed on `record_id`), five DAX measures, visual field wells, and a
validation checklist that must reconcile to the SQL results file.

### 3.8 Verification

Before delivery, all generated artefacts were **deleted and rebuilt from scratch** and checked
with **87 automated assertions**: row counts, per-category issue counts, cleaning invariants
(no nulls, no non-positive volumes, claimed = reference on every clean record, unique keys),
database row counts and foreign keys, SQL result tokens, dashboard structure (5 charts, correct
cell references, KPI values, 55-row register) and README claims. All passed, and every Python
file compiles.

## 4. Results

### 4.1 Data quality outcome

| Check | Records | Severity |
| --- | ---: | --- |
| Distance discrepancy | 17 | High |
| Missing claimed distance | 11 | High |
| High-cost anomaly | 9 | Medium |
| Duplicate record | 8 | Medium |
| Missing company/depot | 6 | High |
| Invalid volume | 4 | High |
| **Total records read** | **408** | |
| **Records with ≥ 1 issue** | **55** | |
| **Clean records** | **353 (86.5%)** | |

Resolved automatically during cleaning: 26 product names standardised, 3 numeric fields
reformatted, 8 duplicate rows removed from the analysis set.

### 4.2 Reconciliation outcome

- **17 discrepancies** above the 20 km tolerance.
- Direction is **mixed**: 7 claimed a longer journey than reference, 10 a shorter one — a
  two-sided pattern, which is what genuine keying/estimation error looks like (one-sided would
  suggest systematic overclaiming).
- Largest single gap: **90 km** (Ndola → Solwezi: claimed 125 km, reference 215 km).
- Indicative value of the overstated distances at the network rate: **~ZMW 49,530** — presented as
  an order-of-magnitude figure for verification, **not** as a loss.

### 4.3 Cost analysis outcome

Network baseline: **0.004431 ZMW per litre-km**; average **1.213 ZMW per litre** across
11,562,000 clean litres.

| Route | Shipments | Cost/litre-km | Vs network | Why flagged |
| --- | ---: | ---: | ---: | --- |
| Lusaka → Chipata | 16 | 0.005046 | **+13.9%** | materiality rule (≥10%) |
| Livingstone → Kazungula | 4 | 0.004966 | **+12.1%** | materiality rule (≥10%) |
| Lusaka → Kitwe | 11 | 0.004250 | −4.1% | **2 high-cost anomalies** on one route |

**3 of 26 routes** flagged. Note the third route is *below* the network average on its aggregate
cost yet still flagged — repeat anomalies on individual shipments that average out at route level.
That is precisely why two rules are used instead of one.

### 4.4 Volume, mix and trend

| Month | Shipments | Volume (L) | Avg cost (ZMW) | Cost/litre-km |
| --- | ---: | ---: | ---: | ---: |
| 2026-07 | 116 | 3,812,000 | 36,494 | 0.004485 |
| 2026-08 | 128 | 4,208,000 | 41,750 | 0.004426 |
| 2026-09 | 109 | 3,542,000 | 40,810 | 0.004447 |

- **Product mix:** Petrol 40.3%, Diesel 36.7% (77.0% combined), Kerosene 14.7%, Jet A-1 8.3%.
- **Regional demand:** Copperbelt 26.4% of clean volume, then Central and Southern.
- **Trend:** volume peaked in August then fell **15.8%** into September while average cost per
  shipment stayed close to its August peak — fewer, more expensive trips.

### 4.5 Accountability view

Exceptions by company (top): ZamFuel Trading Ltd 18 issues (13 High), Great Lakes Energy Ltd 9
(5 High), Rift Petro Supplies Ltd 8 (4 High), Copperbelt Fuels Ltd 7 (6 High) — plus 3 records
where the company itself was not supplied. This is the query that turns "we have data problems"
into "start here".

## 5. Why the results matter

### 5.1 What the data-quality numbers mean operationally

| Finding | Why it matters to the organisation |
| --- | --- |
| **353/408 clean (86.5%)** | Sizes the exception workload: 55 records need human attention, not 408. A reviewer's week is planned by this number. |
| **38 High / 17 Medium severity** | Lets effort be prioritised. Hard failures (missing distance, invalid volume) block downstream arithmetic; statistical flags can wait for a batch review. |
| **17 distance discrepancies** | Directly determines which shipments get pulled against waybills. Without this list, reconciliation means checking every record. |
| **~ZMW 49,530 indicative exposure** | Converts a data problem into a money conversation — small enough to be plausible, large enough to justify verification effort. Hedged as "for verification", never as a loss. |
| **8 duplicates** | Duplicates silently inflate volume totals and can mean duplicate payment. Removing them changes reported volume, so it must be documented, not done quietly. |
| **6 missing company/depot** | An unidentified party or origin blocks attribution, invoicing and allocation — a record that cannot be assigned is a record that cannot be acted on. |
| **4 invalid volumes** | A zero or negative volume makes cost per litre undefined (`inf`), which would corrupt every downstream average if not caught first. |
| **26 product names standardised** | Free-text variants split a single product into four "products" in any pivot table. Fixed at load so reporting matches reality. |

### 5.2 What the analysis enables

- **A shortlist instead of a trawl.** 3 routes out of 26 to review, each with the rule that
  triggered it and the size of the deviation — an investigator can start work immediately.
- **A defensible benchmark.** The 0.004431 ZMW/litre-km network rate becomes the yardstick for
  future tenders, renegotiations or rate reviews: routes sitting persistently above it are the ones
  to re-tender.
- **Two independent signals.** The materiality rule catches structurally expensive routes; the
  repeat-anomaly rule catches routes whose individual trips are expensive even when the average
  looks normal. Lusaka → Kitwe proves the value: aggregate cost is *below* average, yet two
  individual shipments were outliers.
- **Normalising on reference distance** prevents the anomaly test being gamed by the very claim it
  is meant to scrutinise. This is the single most important methodological choice in the project.

### 5.3 What the trend means

Volume down 15.8% while average cost per shipment held near its peak means **unit economics
worsened in September**. On its own it is a watch item, not an alarm — it could be a shift to
longer routes, smaller loads, or seasonal rates. It is exactly the kind of pattern that a
monitoring dashboard exists to surface early.

### 5.4 Why the wording matters

Every output says **"flagged for further investigation"**, never "fraudulent" or "incorrect". A
data analyst's job is to produce evidence, not verdicts: the record shows a discrepancy, the
investigation decides why. Similarly, the exposure figure is labelled as an estimate for
verification. This discipline is what makes the output safe to put in front of a decision-maker —
and it is the same reason confidentiality and labelling are handled strictly throughout.

### 5.6 Honest limits

- The dataset is **synthetic** — it demonstrates method, not domain-specific regulatory knowledge.
- It is a **small, weekend-scale** project: 408 records, one quarter, no production scheduling,
  no data pipeline orchestration, no access controls.
- The advert asks for a minimum of two years' relevant experience; a portfolio project cannot
  substitute for that. It can, however, prove that the actual work — cleaning, validating,
  reconciling, flagging, reporting — has been understood and performed end to end.
- Route flagging rules are **chosen and stated**, not learned from the data; with real data they
  would be calibrated against operational knowledge (terrain, season, contractor terms).

## 6. Reproducing and verifying the project

```bash
pip install -r requirements.txt

python src/generate_data.py        # 408 raw records (seed 42)
python src/data_cleaning.py        # 353 clean, 55 flagged, report written
python src/load_database.py        # 6 tables, 0 FK violations
python src/run_queries.py          # 9 queries → sql/query_results.md
python src/analysis.py             # 3 routes flagged → analytical summary
python dashboard/build_dashboard.py # Excel dashboard rebuilt

python tests\verify_project.py     # 87 assertions → "ALL CHECKS PASSED"
```

Expected control totals after a run: **408 → 353 clean, 55 issues, 26 routes, 3 flagged, 0 foreign
key violations.** Because everything is seeded, any deviation means something changed.

Two operational notes learned the hard way:

- Close output files before re-running a script — an `.xlsx` open in Excel, or a `.md` open in
  Notepad, blocks the write and produces `Permission denied`.
- `record_id` (surrogate) must be used for keys and joins, never `shipment_id` — duplicates share
  the business key by design.

## 7. Talking points

**"Why did you create this project?"**

> When I saw the Data Analyst position, I noticed the role involves more than producing charts —
> it requires collecting, cleaning and validating data, reconciling records, identifying anomalies
> and then turning that information into something useful for decision-making. So I built a small
> synthetic petroleum transportation dataset and a full data-quality and analysis pipeline in
> Python, SQL and Excel, to demonstrate those skills in a context close to the work described in
> the position.

**"Walk me through what you found."**

> 408 records went in; 353 were analysis-ready. The largest issue category was distance
> reconciliation — 17 shipments where the claimed distance differed from the reference by more
> than 20 km, with a maximum gap of 90 km. Using cost per litre-km normalised on reference
> distance, three of 26 routes were flagged for investigation: two because they sit 12–14% above
> the network average, and one because it carried two high-cost anomalies even though its overall
> average looks normal. Everything is reproducible from a seeded script.

**"What would you do with more time?"**

> Add a scheduled refresh with row-level reconciliation against a source system, calibrate the
> anomaly thresholds with operations staff rather than using statistical defaults, add a
> week-on-week alert on cost per litre-km, and build the Power BI version so the register can be
> filtered by severity and company interactively.

**"How do you know your analysis is right?"**

> The project rebuilds from scratch and is checked by 87 automated assertions — counts, cleaning
> invariants, foreign keys, dashboard cell references, and every headline number quoted in the
> README. If a change breaks an assumption, the check fails rather than the number drifting.
